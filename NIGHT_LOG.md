## TASK-03 — хранилище ассетов (готово)
- `server/asset-storage.ts`: `LocalFsAssetBackend` (`<dir>/<hash[0:2]>/<hash>` + `<hash>.mime`, запись через временный файл и `rename`), `S3AssetBackend` (путь «адрес/бакет/aa/хэш», подпись `signS3Request` — AWS SigV4 на `node:crypto` + `fetch`). Подпись сверена с тремя официальными примерами AWS (GET с Range, PUT с «$», список с параметрами) — все совпали. `index.ts` выбирает S3 при `S3_ENDPOINT` и `S3_BUCKET`.
- `server/assets.ts`: `POST /api/assets` (нужна сессия; `{dataUrl}`; хэш — SHA-256 от всей строки, совпадает с `computeAssetHash`; дедупликация; потерянный файл при известной записи дозаписывается; 413 при >15 МБ байтов; 415 не-картинка; 400 мусор), `GET /api/assets/:hash` (`Cache-Control: public, max-age=31536000, immutable`, `ETag`, `nosniff`, `CSP default-src 'none'; sandbox`; inline только png/jpeg/webp/gif/avif, остальное — octet-stream + attachment; `?format=dataUrl` отдаёт исходную строку).
- Решение: в хранилище лежит исходная строка data URL (а не декодированные байты), чтобы клиент мог проверить хэш бит-в-бит; сервер декодирует её при отдаче байтов. Накладные расходы +33%, взамен нет расхождений хэша из-за вариантов записи base64.
- Новая запись в БД — 201, повтор — 200 `deduplicated: true`.
- Клиент `src/asset-store.ts`: `uploadMissingAssets(assets, api)` (по 3 параллельно, запоминает отправленное в сессии), `fetchMissingAssets(project, store, api)` (проверяет хэш скачанного, подмену не кладёт в хранилище, возвращает хэши, которые получить не удалось), `collectAssetHashes`, `markAssetsUploaded`, `resetUploadedAssets`. В `api-client.ts` — параметр `text` для ответов-строк.
- Тесты: `tests/server/assets.test.ts` (22). Всего 825.

- `server/projects.ts`: `GET /api/projects` (JSON-функции SQLite для числа страниц, без разбора всех проектов), `GET /api/projects/:id` (роли host / guest по `?invite=` / viewer; `?pageId=` — одна страница, `canClone: false`, `forbidClone: true`; скрытая или неизвестная страница — 404 `page-not-found`), `PUT` (проверка `parseProject`, 409 `id-taken`, 403 `plan-limit-projects` / `plan-limit-pages` при `ABAX_ENFORCE_LIMITS`, `ownerPlan` и права проставляет сервер, 409 `missing-assets`), `POST …/patch`, `POST …/clone`, `DELETE` (мягкое). Журнал ревизий подрезается до 200 в той же транзакции.
- Решения мелкие: (1) при устаревшем или не заданном `expectedRev` слияние — `preserveElementReactions` + **объединение попыток** по (время, текст) + серверный черновик + объединение веток комментариев по id. `mergeHostTask` для PUT не годится: он отбросил бы попытки, накопленные автором локально в P2P-комнате; при `expectedRev` равном текущей версия клиента — истина (иначе автор не смог бы снять собственную реакцию). (2) Сервер сам выносит `data:image/…` из JSON проекта и из патчей в хранилище, а картинки с чужими адресами и схемами (`https:`, `javascript:`) стираются. (3) PUT в мягко удалённый проект восстанавливает его и считается созданием для лимита; ревизия при удалении не растёт. (4) Клон по спецификации всегда проходит через `projectTaskForRole(…,'guest')` — и у владельца, ответов в копии нет. (5) Гость по приглашению получает ввод учеников и комментарии (он в комнате), публичный зритель — нет. (6) Патч гостя проходит `sanitizeElement` + `guardedElement` (`mergeGuestTask`), владельца — `hostElement`; клиентский `rev` игнорируется.
- Подготовка к комнатам: в `AppContext` — подписки `onProjectChanged` / `onAccessChanged` (комната обновит состояние после REST-записи и отключит участников при удалении проекта или отзыве приглашения), `server/invites.ts` — `findActiveInvite`.
- Тесты: `tests/server/projects.test.ts` (38), `tests/unit/project-access.test.ts` (6). Всего 868.
