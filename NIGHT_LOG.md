- **Google**: `Identity.verifiedEmail`; при входе/привязке `google_email` = нормализованный `email` из `id_token`, только если `email_verified === true` (иначе `null`).
- **Приглашения по почте** — новый `server/email-invites.ts` (5 маршрутов §4.2). У каждого приглашения своя строка `invites` (`kind = 'email'`, своя роль, `page_rights_json = '{}'`). Повтор тому же адресу: `pending`/`accepted` — меняется роль (и `invites.default_role` + событие `invite-updated`), `revoked`/`declined` — новый токен и снова `pending`. Письмо — текст с `inviteUrl` (`<publicWebUrl>/?route=collab&token=…`). Ошибки: `400 bad-email`/`bad-role`/`self-invite` (адрес совпадает с почтой или Google-адресом автора), `404`, `503 mail-disabled`, `429` (20/час на автора), `502 mail-failed` (новое приглашение при сбое почты не остаётся). `GET /api/projects/:id/email-invites` — без отозванных и без токенов. `DELETE` — `revoked` + `invites.revoked = 1` + `invite-revoked` (сокет закрывается 4403). `GET /api/me/invites` — `pending` по `users.email`/`users.google_email`, без удалённых проектов и отозванных токенов; аноним — `[]`. `respond`: только адресату (иначе 404), `accept` → `{ok, token, projectId}`, `decline` → `{ok}` (токен не отзывается).
- **`PUT /api/projects/:id`**: необязательный `baseSig`; `expectedRev < rev` **и** `contentSignature(серверного) !== baseSig` → `409 rev-conflict {rev}` без записи (проверка — до лимитов тарифа). Без `baseSig`, при равной ревизии или совпавшей подписи — прежнее поведение. Ответ `PUT` содержит `sig` (подпись записанного, после слияния), ответ `GET` владельца — `sig` хранимого.
- Интеграционный тест подтвердил: подпись проекта, который клиент отправляет (`AssetStore.extractProjectAssets` → `asset://`, иконка, фон, права с `maxGuests`, `ownerPlan` не тот), совпадает с `sig` ответа `PUT`, `sig` и подписью проекта из `GET` — правка нормализации в `src/sync-conflict.ts` не понадобилась. Подпись проекта с `data:` (до выноса картинок) другая — клиент должен считать её от отправленного вида.
