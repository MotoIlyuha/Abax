## 2. Модель доступа — `src/access.ts` (новый, чистый, без DOM; разрешён серверу)

### 2.1. Роли
```ts
export type AccessRole = 'editor' | 'commenter' | 'reader';
/** Роль в базе и в протоколе: новые значения и старые синонимы Ночей №3–5. */
export type StoredRole = AccessRole | 'edit' | 'view';
export function normalizeRole(raw: unknown): { role: AccessRole; legacy: boolean } | null;
// 'edit' → { editor, legacy: true }, 'view' → { commenter, legacy: true }, новые → legacy: false; иначе null
export function legacyRoleOf(role: AccessRole): 'edit' | 'view'; // editor → 'edit', commenter/reader → 'view'
```
- Владелец — отдельный статус (`owner: true`), не роль. «Нет доступа» — отсутствие разрешения, не роль.
- Старый `'view'` показывается в интерфейсе как «Комментатор (старая ссылка)», `'edit'` — «Редактор»; поведение старых токенов не меняется (сейчас `view` уже комментирует, реагирует, отвечает в заданиях, пишет в чат, пользуется указкой).

### 2.2. Итоговое право на странице
```ts
export interface PageAccessInput {
  owner: boolean;
  role: AccessRole;
  legacy: boolean;
  /** Право страницы из project.permissions.pageRights. */
  pageSetting?: PageRight;
  /** Личное право участника на страницу (таблица участников P2P; старые записи invites.page_rights_json). */
  personal?: PageRight;
}
export function effectivePageAccess(a: PageAccessInput): PageRight;
```
Порядок (первое сработавшее правило):
1. `owner` → `'edit'`.
2. `personal` задано → `personal`.
3. `pageSetting === 'hidden'` → `'hidden'`.
4. `legacy` → `pageSetting ?? (role === 'editor' ? 'edit' : 'view')` (как сейчас: `edit` страницы повышает старую ссылку `view`).
5. `pageSetting === 'view'` → `'view'`.
6. иначе → `role === 'editor' ? 'edit' : 'view'` (`edit` страницы новую роль **не** повышает).

Примеры (обязательны в тесте):
| Вход | Итог |
|---|---|
| Читатель (новая роль) + страница `edit` | `view` |
| Старая ссылка `view` + страница `edit` | `edit` (как сейчас) |
| Редактор + страница `hidden` | `hidden` |
| Редактор + страница `view` | `view` (комментировать может — §2.3) |
| Личное `view` поверх страницы `hidden` | `view` |
| Владелец + страница `hidden` | `edit` |

`invitePageRight` в `src/project-access.ts` реализуется через `effectivePageAccess` (личное право = `invite.pageRights[p]`, старые записи с непустыми правами работают как раньше).

### 2.3. Возможности участника
```ts

export function participantCaps(a: { owner: boolean; role: AccessRole; inviteAllowCopy?: boolean }, perms: ProjectPermissions | undefined): ParticipantCaps;
```

## 4. Защита чужих элементов

### 4.1. Где принимается решение
Только хаб и сервер. Чистый модуль `src/element-guard.ts` (разрешён серверу):
```ts
export interface GuardWho { privileged: boolean; principal: string | null; protect: boolean }
export interface GuardResult { patch: BoardPatch; refused: { ids: string[]; order: boolean; page: boolean } }
export function guardPatch(known: Page, patch: BoardPatch, who: GuardWho): GuardResult;
export function guardPageReplace(known: Page, incoming: Page, who: GuardWho): { page: Page; refused: boolean };
```
`privileged` — владелец (любое устройство). Правила для не-владельца:
- `put` нового id → `by = principal` (присланное `by` игнорируется); при `principal === null` — элемент без защиты не создаётся (отклоняется).
- `put` существующего: задание → `mergeGuestTask` (ответ в чужой карточке разрешён по `caps.comment` — отдельный путь `task-*`, здесь — как сейчас); иначе при `protect` и `known.by !== principal` → отклонить; иначе принять с `by = known.by`.
- `del` при `protect` и `known.by !== principal` → отклонить.
- `order` при `protect`: принять, только если взаимный порядок чужих элементов не изменился.
- `grid` / `backgroundColor` / `coordLabels` при `protect` → отклонить (поле `page: true`).
Для владельца: `put` — `hostElement` + `by` из известного (у новых элементов владельца поля `by` нет).
Без `protect` новые элементы гостей всё равно получают `by` (чтобы защиту можно было включить позже).

### 4.2. Кто автор (`principal`)
| Случай | Решение |
|---|---|
| Вошедший пользователь, два устройства | `u:<userId>` из проверенной сессии — одинаков на обоих |
| Анонимный гость облака, переподключение | при входе по ссылке клиент вызывает `api.ensureSession()` (анонимный пользователь устройства), сессия уходит в `hello` → `u:<userId>`; тот же браузер — тот же автор |
| Гость P2P/LAN/ретранслятора | хаб выдаёт `principal = c:<12 hex>` и секрет возобновления (§4.3) |
| Офлайн-рисунок | офлайн рисует только владелец; его элементы без `by` |
| Старый `.doska` без сведений | элементы владельца |
Имя, цвет курсора, `cursorId`, `m.userId` и любое присланное клиентом значение автором **не являются**.

### 4.3. Секрет возобновления (только P2P-хабы)
- Новый участник без `access.principal` получает в `init` поля `principal` и `resume` (128 бит из `crypto.getRandomValues` / `crypto.randomBytes`, base64url). Хаб хранит `resume → principal` в памяти комнаты.
- Клиент хранит секрет в `sessionStorage['doska.resume.<код комнаты>']` и сразу после `init` шлёт `{t:'resume', secret}`. Хаб: секрет известен и его `principal` не занят другим открытым соединением → `principal` участника заменяется, ответ `{t:'resume', ok: true}`, `{t:'users'}`; иначе `{t:'resume', ok: false}`. `resume` после первого `patch`/`project` участника игнорируется.
- Секрет в проект, файл и `users` не попадает.

### 4.4. Отказ
- Хаб применяет только разрешённую часть и шлёт **отправителю** исправляющий `{t:'patch', pageId, rev, ops, by: -1}`: `put` известных версий отклонённых id, полный `order` хаба при отказе в порядке, `grid`/`backgroundColor`/`coordLabels` хаба при отказе в настройках страницы.
- Полный проект от гостя (`mergePages`): каждая страница — `guardPageReplace`; при отказе отправителю уходит `{t:'project', project: projectFor(c), by: -1}`. При `protect` новые страницы от гостя не принимаются.
- `POST /api/projects/:id/patch?invite=`: отклонённые операции отфильтровываются, ответ `{ ok, rev, refused: string[] }`.

### 4.5. Живые поля и подписи
- `by` — поле хаба (как реакции): `hostElement`, `guardedElement`, `mergeStale` переносят его из известного элемента с тем же id; у новых элементов в PUT владельца `by` остаётся как прислано (владелец доверенный).
- `contentSignature` (`src/sync-conflict.ts`) пропускает ключ `by` у элементов — подписи проектов без `by` не меняются; старый клиент, потерявший `by`, не даёт ложного `409 rev-conflict`.
- Реакции, комментарии и ввод в задания — отдельные сообщения, защита их не касается.

### 4.6. Клиент (удобство, не безопасность)
- `canTouchElement(el)` в `src/collab.ts`: не в комнате / хост / `!protectElements` → `true`; иначе `el.by === myPrincipal()`.
- `src/controller.ts`: попадание, ластик и частичный ластик, рамка выделения, «Выделить всё», перенос, стрелки, Delete, группировка, слои, стиль из панели, двойной клик в текст — пропускают чужие элементы. Наведение на чужой элемент — курсор `not-allowed` и подсказка «Элемент преподавателя» (`by` нет) или «Элемент другого участника».

### 5.2. Общая ссылка
- `POST /api/invites` принимает `defaultRole` из пяти значений и `enabled?: boolean`. Защита от молчаливого расширения: если сохранена новая роль, а пришёл старый синоним, равный `legacyRoleOf(сохранённой)`, роль не меняется.
- `enabled: false` → `disabled_at = now` + событие `invite-revoked` (сокеты по ссылке и по именному адресу закрываются 4403); `enabled: true` → `disabled_at = NULL` (тот же токен — напечатанные ссылки снова работают).
- `POST /api/invites/:token/reset` (владелец) → старый `revoked = 1` + `invite-revoked`; новый токен с теми же ролью, копированием и паузой. Ответ — как у `POST /api/invites`.
- `GET /api/invites?projectId` возвращает ссылку и на паузе (`enabled: false`). `DELETE /api/invites/:token` — как раньше (старые клиенты). Отозванные в Ночь №5 ссылки остаются отозванными.
- Ответ ссылки: прежние поля, `defaultRole` — старый синоним (`legacyRoleOf`), новые `role` (как хранится), `enabled`, `alias` (активный именной адрес или null), `url`.
- `findActiveInvite` не выдаёт ссылку на паузе.

### 5.3. `/j/:x` и именной адрес
- `GET /j/:x` с `Accept: application/json` — как сейчас (через общий разбор §5.4). Иначе, если `x` — токен или именной адрес по форме → `302 Location: <publicWebUrl>/?route=collab&token=<x>`; иначе — 404. Клиент по вложенному пути не отдаётся.
- Красивая ссылка строится от `publicWebUrl` (`PUBLIC_WEB_URL`) только если он указывает на сервер, раздающий клиент; в остальных случаях (GitHub Pages) — прежний формат с параметрами. Признак — опция сервера `prettyLinks` (по умолчанию `true`, если задан `staticDir`) в ответе ссылки: поле `prettyUrl` (`<publicWebUrl>/j/<token>` или `/j/<alias>`) или `null`.
- Маршруты (владелец, `requireUser`):
  - `GET /api/projects/:id/alias` → `{ alias: string | null, former: string[] }`;
  - `PUT /api/projects/:id/alias {alias}` → 400 `bad-alias` (не `isAliasShaped`), 403 `plan-limit-alias` (Free при `enforceLimits`), 409 `alias-taken` (занят или когда-либо принадлежал другому аккаунту, в т.ч. надгробие), 429 `alias-limit` (больше `MAX_ALIASES_PER_OWNER` записей у владельца). Прежний активный адрес доски → `former` (продолжает вести на доску). Свой `former`/`released` адрес можно занять снова (в т.ч. для другой своей доски — интерфейс предупреждает).
  - `DELETE /api/projects/:id/alias/:alias` → `released` (не ведёт никуда; другим аккаунтам недоступен навсегда).
- Удаление аккаунта владельца → `owner_id = NULL` (надгробие, никому не достаётся).

### 5.4. Разбор токена или адреса — один путь
`findActiveInvite(app, x, projectId?)` (и всё, что её вызывает: `GET /api/invites/:x`, `/j/:x`, `hello.invite`, `GET /api/projects/:id?invite=`, `/patch?invite=`, `/clone?invite=`):
- `isTokenShaped(x)` → как сейчас + не на паузе;
- `isAliasShaped(x)` → строка `public_aliases` в состоянии `active` или `former`, доска не удалена, владелец Pro/Tutor (при `enforceLimits`), у доски есть общая ссылка не на паузе → права этой ссылки с `via: 'alias'`. **Токен ссылки клиенту не раскрывается**: в ответах `token` = сам адрес.
- Отказ — 404 с кодом: `invite-not-found`, `link-paused` («Автор закрыл доступ к доске по ссылке»), `alias-released` («Адрес больше не используется»), `alias-inactive` («Адрес временно неактивен»), `board-deleted` («Доска удалена»).
- `InviteRights` получает `role`, `legacy`, `via: 'token' | 'alias'`, `linkToken` (настоящий токен — только для сервера), `inviteId`/`kind`.

### 5.5. Приглашения по почте
- `role` — пять значений, по умолчанию `'editor'`; `allow_copy` по-прежнему 1 (копирование решает доска, §2.3).
- `GET /api/projects/:id/email-invites` добавляет `lastUsedAt`.
- `last_used_at` обновляется в `join()` облачной комнаты и в `resolveInvite` (не чаще раза в минуту на токен).

### 5.6. Облачная комната
- `Conn`: `linkToken` (разрешённый), `source`, `inviteId`, `userId`. `invite-revoked` закрывает соединения с совпадающим `linkToken` (вход по адресу тоже).
- `attach(..., { access: { role, legacy, personal, inviteAllowCopy, source, inviteId, principal: user ? 'u:'+user.id : null } })`; `room.inviteAllowCopy` удаляется (D1).
- `invite-updated` пересчитывает `access` соединений с этим `linkToken`.

### 5.7. REST и просмотр (D2, D7)
- `viewFor` и `invitePageRight` — через `effectivePageAccess`; ответ гостю: `defaultRole` — старый синоним, новые `role`, `caps`.
- `GET /api/projects/:id` без приглашения и не владельцу: `permissions.linkView === false` → 404 `project-not-found` (неотличимо от несуществующей доски).
- `POST /api/projects/:id/clone`: не владелец — `forbid_clone` как сейчас; с `invite` — дополнительно `caps.copy` участника этой роли; без `invite` — дополнительно `linkView !== false`.
- `/patch?invite=` — право страницы через `effectivePageAccess` + `guardPatch` (§4.4).

## 11. Locked Decisions
Нумерация вопросов предполётного согласования 1–21 сохранена; приняты рекомендации по умолчанию, кроме №14.

**А. Организация**
0.1. **Git перед стартом.** Файлы `SPEC_NIGHT6.md`, `TASKS.md`, `AGENTS.md` подготовлены в рабочей копии (не закоммичены). Агент:
   1. `git fetch origin`; проверить, что `origin/main` = `d24fa24` и содержит `2c58e43` (`git merge-base --is-ancestor 2c58e43 origin/main`);
   2. подтянуть локальный `main` до `origin/main` **без checkout** (на `main` в рабочей копии лежит старый `TASKS.md`, checkout с несохранёнными файлами упадёт): `git branch -f main origin/main` (только если локальный `main` — предок `origin/main`, т.е. перемотка);
   3. `git switch -c night/6 main` (деревья `night/5` и `main` совпадают — подготовленные файлы переносятся);
   4. `git mv NIGHT_LOG.md NIGHT_LOG_NIGHT5.md`, создать новый `NIGHT_LOG.md` («журнал ночного запуска #6»);
   5. первый коммит: `SPEC_NIGHT6.md`, `TASKS.md`, `AGENTS.md`, `NIGHT_LOG_NIGHT5.md`, `NIGHT_LOG.md`.
   Тег `v2.10.0` агент не ставит.
0.2. Базовая линия — по журналу Ночи №5: 1327 unit/server и 314 E2E; агент перепроверяет её первым прогоном (`npm test`, `npx playwright test --list`) и пишет фактические числа.
0.3. **Новых npm-зависимостей нет** (ни `dependencies`, ни `devDependencies`), вендорных библиотек тоже.

**Б. Решения по вопросам**
1. Соавтор и членство аккаунтов — Ночь №7. В v1 выдаются Редактор / Комментатор / Читатель + Владелец. По общей ссылке и токену из письма управление доступом не выдаётся никогда.
2. Старые роли: `edit` → «Редактор», `view` → «Комментатор (старая ссылка)»; поведение старых токенов не меняется.
3. Право страницы для новых ролей — потолок («По роли / Только просмотр / Скрыта», `edit` не повышает); старые токены сохраняют повышение `edit`; при смене роли ссылки — предупреждение (§7.1).
4. Личные права (таблица участников P2P, старые `page_rights_json`) — выше права страницы; в облаке новых личных прав по страницам нет.
5. Читатель читает чат, но не пишет; без указки и реакций. Комментатор — всё это может.
6. `permissions.summon`: «Только я» (по умолчанию) / «Я и редакторы». «Автопереход за мной» — только владелец.
7. Исправить D1; копирование — флаг доски `permissions.allowCopy`, считается на участника; редакторы копируют всегда; честная подпись про снимки экрана.
8. `permissions.linkView` (по умолчанию включён у существующих досок); при выключении общей ссылки — галочка «И закрыть просмотр по ссылке на доску».
9. Тумблер общей ссылки — пауза (тот же токен); «Сбросить ссылку» — новый токен; отозванные в Ночь №5 остаются отозванными.
10. `/j/` — только на домене сервера, HTML-запрос получает `302` на `?route=collab&token=`; GitHub Pages — прежний формат с параметрами.
11. Именной адрес: 3–23 символа `[a-z0-9-]`, с буквы, резерв, Pro/Tutor, один активный на доску, до 20 записей на аккаунт; длина 24 — за токенами.
12. При переименовании старый адрес ведёт на ту же доску до «Освободить»; освобождённый никогда не достаётся другому аккаунту; на Free — «временно неактивен».
13. Токен ссылки при входе по адресу не раскрывается: сервер принимает адрес везде, где сейчас токен.
14. **QR-код не делается вовсе.** Пользователи Abax работают на ПК, ноутбуках и планшетах; для ввода без мессенджера достаточно именного адреса и короткого кода LAN-комнаты. Никаких `src/vendor/qrcodegen.ts`, `src/qr.ts`, `jsqr`; кнопок `[QR]` в окне нет.
15. Защита чужих элементов — на всех тарифах, по умолчанию выключена.
16. Автор элементов: в облаке — `u:<userId>` (гость получает анонимную сессию устройства через `ensureSession`); в P2P — `c:<id>` + секрет возобновления от хаба.
17. Элементы без `by` — элементы владельца.
18. При включённой защите редакторы не добавляют страницы и не меняют фон, сетку, подписи осей и имя страницы; без защиты — как сейчас.
19. `invites.last_used_at`, подписи «отправлено, ещё не заходил» / «заходил(а) <дата>», «личная ссылка, её можно переслать»; пункта «отозвать доступ у человека» нет.
20. LAN: все IPv4 с именами интерфейсов, loopback — с пометкой «только на этом компьютере»; код комнаты — 8 символов из `crypto.randomBytes`.
